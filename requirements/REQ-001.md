## Context

REQ-001 is the frozen north star: the one-paragraph statement of what this fork is for and
who it serves. Every later REQ either advances this or is out of scope. It is deliberately
hard to change — supersede it with a new REQ rather than weakening it.

This repository is a fork of [Tandoor Recipes](https://github.com/TandoorRecipes/recipes),
a self-hosted, multi-tenant recipe manager (Django + DRF backend, Vue 3 SPA). The fork
exists to run and shape Tandoor for the owner's own household, and to keep every local
change *legible and re-appliable* across upstream rebases. Local work is the point;
upstreaming is opportunistic — a feature is offered to upstream when it looks generally
useful and upstream signals it is welcome, but the fork never blocks on that. The owner is
not, and does not intend to become, a principal upstream contributor.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | The fork serves the owner's own deployment first | It is the only user whose needs are certain; upstream's roadmap is not ours to steer |
| 2 | Every local change is a tracked REQ, not an ad-hoc commit | The value of the fork is being able to rebase on upstream and know exactly what is ours and why |
| 3 | Upstreaming is opportunistic, never a precondition | Waiting on upstream discussion/CLA/review would stall work that already has a user |
| 4 | Upstream's invariants are not ours to break casually | Space scoping, the `guest`/`user`/`admin` groups, and the generated API client are load-bearing; diverging from them makes future rebases expensive (see CLAUDE.md § Architecture) |
| 5 | Do not diverge from upstream where a config or plugin would do | `recipes/plugins/<name>/` and settings are the cheap seams; forked core code is the expensive one |

## Requirement

This fork delivers a Tandoor deployment that fits the owner's household, with every local
divergence from upstream recorded as a REQ so it survives rebasing onto upstream `develop` —
and so any individual change can be offered upstream on its own merits when worthwhile.

```yaml acceptance
- id: AC1
  text: >
    The project builds from a clean checkout — Django's migration state is consistent
    with the models, so no model change is carrying an un-generated migration. The
    companion half of this criterion, that the suite itself passes, is enforced on every
    land by the engine's configured full-suite run rather than restated here (see Notes).
  test: 'python -m pytest cookbook/tests/other/test_baseline.py::test_no_missing_migrations --no-cov'
  check: regression
  status: pending
```

## Notes

Keep this REQ short — it is a compass, not a specification.

**AC1 was reworked on 2026-07-30** (see [plan 0001](../docs/plans/0001-north-star-green-baseline.md)).
As written at onboarding it named the whole suite, `PYTEST_ADDOPTS="--no-cov" python -m pytest`,
and could not satisfy the gate for two independent reasons. The command could not execute
— the engine rebinds only a *leading* `python` to `verify.python`, and this workstation
has no ambient `python`. And a *named* acceptance test may not skip (skip ≠ green), while
the suite legitimately skips 18 PostgreSQL-only tests, so naming the suite as a criterion
is self-defeating. The whole-suite guarantee was never lost: `verify.full_suite` in
`.devsteward/config.yaml` runs it at every land for every REQ, and correctly tolerates
skips there. AC1 now names the non-redundant half — that the project builds. The
requirement itself is unchanged.

**Known gap, not silently deferred:** the suite defaults to SQLite, so 18 search tests
marked `requires PostgreSQL` never execute locally, while production runs PostgreSQL 16.
CLAUDE.md § Tests already warns that Search and Food behaviour differs between the two
backends. Closing that gap means running the suite against PostgreSQL via the `TEST_*`
env vars — an environment-bound concern that should not be attached to the north star's
own acceptance. Home: a follow-on REQ, to be intaken when a REQ first touches search or
food behaviour.

Onboarded under DevSteward on 2026-07-30 via `/onboard`. Branch model for this project is
`master` (production) / `develop` (integration) — upstream's names, *not* DevSteward's
default `main`/`dev`; see `.devsteward/config.yaml`. `origin` still points at
`TandoorRecipes/recipes` (read-only for us); a personal fork can be added later with
`gh repo fork --remote` without affecting any DevSteward state.
