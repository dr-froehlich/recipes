## Context

Tandoor holds two unrelated notions of time and calls them by overlapping names.

`Recipe.working_time` and `Recipe.waiting_time` (`models.py:1102-1103`) are two hand-entered
integers of minutes. Nothing computes them — a grep across the backend finds no aggregation
over steps anywhere. They are exactly what an author typed, or what an importer wrote.

`Step.time` (`models.py:966`) is a single untyped integer. It is neither working nor waiting:
upstream's only use for it is a stopwatch, `StepView.vue:12-23` handing `step.time * 60` to a
countdown. REQ-004 then formalized the only reading that makes sense of it — **elapsed wall
clock** — by back-chaining start times over it (Decision 1). A step's `time` is how long the
step occupies, whether the cook is present or not.

So the split exists only where it is least useful, at the level of the whole recipe, and is
missing where it would actually drive behaviour: per step, where it answers *do I have to be
in the kitchen for this*. The two clocks do not agree and nothing reconciles them — REQ-004's
context recorded the household's Pizza recipe as the standing example, waiting time 2400 min
against a longest single step of 1440 min.

**This is a known-flawed upstream design, not an accident.** Issue
[#1882 "Time Rework"](https://github.com/TandoorRecipes/recipes/issues/1882), opened by the
maintainer in June 2022 and still open, lists as its first unchecked box: *"connect step and
recipe times possibly with a button to calculate recipe time based on steps or by removing it
from the recipe completely and just querying the totals from the steps."* Its third box admits
the recipe-level naming does not even match schema.org. Issue
[#3587](https://github.com/TandoorRecipes/recipes/issues/3587) (March 2025) proposes per-step
time *types* so the totals compute themselves; it has never received a reply. Issue
[#4643](https://github.com/TandoorRecipes/recipes/issues/4643) asked for named baking phases
and was closed the same day with *"You can add time to a step"*; the reporter's objection —
*"I have to add 4 or 5 steps for each one"* — went unanswered until the maintainer wrote in
June 2026 that it *"adds a lot of complexity just for this usecase. For now multiple steps
need to suffice, maybe I will improve time management in the future."* Nothing upstream is
going to fix this, so the fork does (REQ-001 Decision 1).

Two facts about this checkout shaped the design more than anything else.

**No importer writes `Step.time`.** All 17 integration classes plus the URL scraper write the
recipe-level pair — `recipe_url_import.py:80,87` maps schema.org `prepTime` to `working_time`
and `cookTime` to `waiting_time`, which is already semantically wrong since cook time is
usually attended — but not one of them sets a step duration. Every per-step time in this
household's collection was typed by hand. Any design that makes the recipe fields unwritable
would therefore break all 18 import paths *and* blank the times on every recipe already
imported.

**`Step.time` already means elapsed, in shipped and deployed code.** REQ-004's scheduler and
`StepView.vue`'s timer both depend on that reading. Redefining `time` to mean *working* time —
the shape that would mirror the recipe pair most prettily and read best as an upstream PR —
would silently reinterpret every existing value: this household's 12-hour bulk ferments would
start displaying as twelve hours of labour, and both shipped features would need changing.
Adding the attended portion *inside* the existing elapsed value costs one optional field and
changes the meaning of nothing.

The remaining awkwardness is honest and worth stating: a legacy step with `time` 10 and no
working portion reads as ten unattended minutes, which is wrong for a knead. That error is
visible, one field wide, and corrected by editing the step — unlike the alternative's error,
which is loud, wholesale, and spread across every long step in the collection.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | `Step.time` keeps its present meaning — **total elapsed minutes** — and gains one optional sibling, `Step.working_time`, the **attended portion inside it**. Waiting is derived as `time − working_time` and is never stored | The only reading of `time` that is already true in shipped code (REQ-004 Decision 1, `StepView.vue`'s timer). Additive: the new field defaults to 0, so nothing changes until an author fills it in, and REQ-004 and the timer need no change at all. The rejected alternative — redefining `time` as working time beside a new `waiting_time`, mirroring the recipe pair — would reinterpret every existing value as labour and force changes to two shipped features |
| 2 | Within a step, the **work comes first and the wait follows it** | "Mix the dough (10 min), then bulk ferment (4 h)" is how bread recipes are actually written, and it composes correctly with REQ-004's backward chain: the cook arrives at the step's start, works, then the dough waits until the next step begins. The wait-then-work case is expressible by putting the wait on the preceding step, where it already belongs |
| 3 | `Step.working_time` may never exceed `Step.time`, enforced at the model and the serializer | Otherwise waiting goes negative and every derived total downstream is nonsense. The editor makes the violation unreachable by construction (Decision 7), so the validation guards the API, the admin and scripts |
| 4 | A recipe's totals are **materialized, not computed on read**: whenever its steps change and their elapsed times total more than 0, `working_time` and `waiting_time` are recomputed and **written to the recipe's columns** | `RecipeCard.vue:31-32` reads these fields for every card in a 50-row list, and the export and schema.org paths read them too. Keeping the columns true means no read path has to remember to annotate, no external API consumer sees a stale number, and the database never holds a second clock. The cost is a write side-effect on step saves and one backfill migration |
| 5 | Recipe times stay **editable exactly as today while the steps total 0 elapsed**, and become **derived and locked** the moment they do not. The lock is enforced at the API and reflected in the UI | The household's rule, and the only one that keeps 18 import paths working: an imported recipe has no step times, so it behaves precisely as it does now. Once someone starts timing the steps, the steps win — a curated total that contradicts the steps printed beneath it is the defect this REQ exists to remove |
| 6 | The lock **rejects** writes from the two paths a person types into — `RecipeSerializer` updates and the batch-edit endpoint — but **accepts and then overwrites** on create and on the import/export serializers | A Tandoor-to-Tandoor export round trip carries both the recipe totals and the step times in one payload; rejecting it would break the fork's own export format and `RecipeExportSerializer`. Accepting and letting materialization win is the same outcome the household's rule states — "imported values are overwritten if step times show >0" — without an error path that no human asked for |
| 7 | The step editor shows **Working** and **Waiting** boxes, storing `time = working + waiting` and `working_time = working`. The raw elapsed value is no longer typed directly | The author states the two durations they actually know instead of doing subtraction, `working > time` becomes unreachable, and the model's asymmetry stays invisible where it would only confuse. Both labels already exist as translation keys (`WorkingTime`, `WaitingTime`), so no new weekday-style key sprawl |
| 8 | The working/waiting ↔ `(time, working_time)` conversion lives in a **plain TypeScript module**, not inside the editor component | The fork has no component tests (CLAUDE.md § Conventions); REQ-004 established that the way to make frontend logic gradable is to keep it a pure function in `src/utils/`. A conversion buried in a `.vue` file could not be an acceptance criterion |
| 9 | Sub-recipe steps are **not** recursed into: a step carrying a `step_recipe` contributes only its own `time` and `working_time` | Consistent with REQ-004 Decision 7, which made the same call and flagged rather than recursed. Diverging here would give the schedule and the totals two different notions of a sub-recipe's cost |
| 10 | The backfill migration is proven against the **household's live collection inside the develop session**, not deferred to validation | The migration's only real risk is corpus-shaped — which existing recipes have partially timed steps, and what their curated totals become. The System Tester runs in a fresh session that never sees the diff and cannot fix anything, so a red there costs a whole session; this belongs where it is fixable in place (see Notes) |
| 11 | REQ-004's schedule is **untouched** by this REQ | Decision 1 keeps `Step.time` meaning what the scheduler already assumes, so there is no correctness obligation. Showing which stretches of the schedule are attended is the payoff, and it is a clean separate increment homed in a named follow-on REQ |

## Requirement

A step records how much of its duration the cook is actually present for, and a recipe's
working and waiting totals stop being an independent claim and start being the sum of its
steps.

### The step model

`Step` gains `working_time`, an optional integer of minutes defaulting to 0, meaning the
attended portion of the step's existing `time`. `Step.time` continues to mean total elapsed
minutes and is unchanged in meaning, in the timer, and in REQ-004's schedule. The waiting
portion is `time − working_time` and is never stored.

`working_time` may not exceed `time`. A write that violates this is rejected with a validation
error, at the API and at the model, on every path — the step endpoint, nested writes through a
recipe, the import serializers and the Django admin.

### The recipe totals

For any recipe, let `elapsed` be the sum of `time` across its steps.

- **`elapsed == 0`** — the recipe's `working_time` and `waiting_time` behave exactly as they do
  today: stored, hand-editable, written by every importer and by the URL scraper, and untouched
  by this REQ.
- **`elapsed > 0`** — the recipe's `working_time` is `sum(step.working_time)` and its
  `waiting_time` is `sum(step.time − step.working_time)`. These values are **written to the
  recipe's columns**, superseding whatever was stored, and a person may no longer type them.

Recomputation fires on every path that can change a recipe's step times: a step saved or
deleted through `StepViewSet`, a step written nested inside a recipe, and a change to the
recipe's `steps` relation. A step may belong to more than one recipe, so recomputation applies
to every recipe in the step's `recipe_set`.

A data migration performs the same recomputation across the existing collection, so the
invariant holds from the first deploy rather than from each recipe's next save.

### The edit lock

While a recipe's steps total more than 0 elapsed minutes:

- `RecipeSerializer` **rejects** an update that sets `working_time` or `waiting_time`, with an
  error naming the reason.
- The batch-edit endpoint (`api.py:1980-1984`) **rejects or skips** affected recipes rather
  than issuing the queryset `update()` that would bypass every save hook.
- `RecipeEditor.vue:54-57` and `BatchEditRecipeDialog.vue:65-68` **disable** the two inputs and
  state that the values come from the steps.

Recipe **creation**, `RecipeExportSerializer` and the import serializers are not rejected: they
accept the submitted totals, and materialization overwrites them once the steps land. A
Tandoor-to-Tandoor export round trip therefore still imports cleanly.

Setting every step's time back to 0 returns the recipe to hand-edited totals.

### The step editor

The step editor's single optional **Time** input becomes two optional inputs, **Working** and
**Waiting**, reusing the existing `WorkingTime` and `WaitingTime` translation keys. It stores
`time = working + waiting` and `working_time = working`. An existing step with `time` 720 and
no working portion opens as Working 0 / Waiting 720.

The conversion in both directions is a pure function in a plain TypeScript module.

### The step display

Where a step currently shows one duration, it shows the working and waiting portions when both
are non-zero, and a single duration when only one is — all rendered through REQ-003's readable
formatting, so a four-hour ferment reads `4 h`. The stopwatch button continues to count down
`time`, unchanged.

## Notes

**Process declarations, made at intake (2026-08-16).** `develop: fused`, `concept: false`,
`lab: []` — all defaults, so the `process:` block is omitted. The shape was fully specified by
the intake interview, the acceptance criteria were writable on the day, and the one substantial
hazard is a documented procedure rather than an unknown.

**That hazard: the OpenAPI client.** This is the fork's first REQ to change the Django model,
so it drags in a migration, serializer changes, and a regeneration of `vue3/src/openapi/`.
CLAUDE.md § Regenerating the API client documents the trap in this checkout — the committed
client was generated with the enterprise and open-data plugins installed, which this checkout
lacks, so a naive regeneration deletes ~40 plugin model files and two thirds of `ApiApi.ts`.
The procedure is: regenerate, then `git checkout -- vue3/src/openapi` and restore only the
model files this change actually touches (`Step`, `Recipe` and their patched variants). Run the
generator with `PYTHONPATH=$(pwd)`.

**Live proof is a develop obligation, not an acceptance criterion (Decision 10).** The backfill
migration must be run against the household's real collection during the develop session, which
may deploy as often as the iteration needs and fix what it turns up in place. What that run has
to establish: which existing recipes have *partially* timed steps, and whether their newly
derived totals are acceptable. AC1 proves the mechanism against synthetic fixtures; only the
real corpus can show what the mechanism does to real data.

**Accepted data loss, stated plainly.** Materialization overwrites. A recipe with a curated
waiting time of 2400 whose steps currently total 1440 will end up with 1440, and the 2400 is
gone rather than shadowed — this is the household's stated rule ("imported values are
overwritten if step times show >0") and its direct consequence. Partially timed recipes will
therefore show *smaller* totals than before until their remaining step times are filled in. The
recovery path is exact: complete the step times, or zero them all to return the recipe to
hand-edited totals. The develop session should record the pre-migration values of every affected
recipe before the migration runs on the deployment.

**Known limitation, homed not deferred.** A legacy step carrying only an elapsed time reads as
fully unattended, which is correct for a ferment and wrong for a knead. This is inherent to
Decision 1 and is corrected one step at a time by editing; no migration can infer which legacy
durations were attended. It is a display consequence of missing data, not a defect in the
mechanism, so it has no follow-on REQ — but it is why AC5 asks the tester to confirm the
Working 0 / full-duration-Waiting opening state explicitly rather than treating it as a bug.

**Scope boundaries.** REQ-004's schedule is untouched (Decision 11): it continues to chain over
`Step.time`, which still means elapsed. Showing which stretches of a bake schedule are attended
— "be in the kitchen 06:00–06:10, then free until 14:00" — is the payoff of this REQ and is a
**named follow-on REQ**, to be intaken once this has run in the household's kitchen. Also out of
scope: recursion into sub-recipe steps (still homed in REQ-004's follow-on), a third "cooking"
category as issue #3587 and #1047 request, changing the recipe-level field *names* to match
schema.org (#1882 box 3), sub-minute or float durations (#2748), and any change to how the
importers or the URL scraper map external time fields — they keep writing the recipe pair, and
that write keeps working because imported recipes have no step times.

**Upstream.** Not part of this REQ (REQ-001 Decision 3), and deliberately so. Issue #1882 box 1
asks for exactly this and has been open since 2022; #3587 proposes the per-step split and has
never been answered; #4643 was closed as too complex for the use case. A comment offering the
REQ-004 work is already sitting unanswered on #1882 as of 2026-08-13. Decisions 1, 5 and 6 keep
the change additive and backward-compatible — no field renamed, no existing value reinterpreted,
no import path broken — so it stays offerable later if upstream ever signals interest. REQ-005
remains the fork's live upstream offer.
