## Context

REQ-006 put the household's collection into Tandoor — 270 recipes, 2639 ingredient rows,
0 errors. The structure came through intact. What came through *misparsed* is the inside of
the ingredient lines, and it is visible in the space today:

```
"1 reife Avocado"        -> amount 1, unit "reife",     food "Avocado"
"2 Scheiben altes Brot"  -> amount 2, unit "Scheiben",  food "altes Brot"
"1 gehäufter Tl Senf"    -> amount 1, unit "gehäufter", food "Tl Senf"
"4 – 5 große Tomaten"    -> amount 4, unit "–",         food "5 große Tomaten"
```

`IngredientParser` takes the token after the amount as the unit. When that token is a German
adjective the adjective becomes a unit, and — worse — the *real* unit is pushed into the food
name. The measured damage over 2666 ingredient rows in the live space:

| | units | rows |
|---|---|---|
| real units (`g`, `El`, `ml`, `Tl`, `Bund`, …) | 45 | 1410 |
| adjectives (`große`, `rote`, `reife`, `gehäufter`, …) | 30 | 91 |
| range fragments (`–`, `–6`, `½-2`) | 7 | 15 |
| nouns pressed into service as units | 17 | 46 |

and on the food side, **513 of 773 foods are used exactly once** — a list that will never roll
up on a shopping list, because `IngredientParser.get_food` matches **exactly** on `name` or
`plural_name`. There is no fuzzy or partial matching: `Avocado` and `Avocados` are two foods
today, and `Tl Senf` will never meet `Senf`.

The target shape was named at intake: `1 reife Avocado` should become **amount 1, no unit,
food `Avocado`, note `reif`**. That shape is already reachable — `1 Avocado, reif` parses to
exactly `(1.0, None, 'Avocado', 'reif')` through the parser's existing comma rule, and
`1 Tl Senf, gehäuft` to `(1.0, 'Tl', 'Senf', 'gehäuft')`. Nothing in the parser needs to
change. What is missing is a rewrite of the raw line **before** it is tokenized, and no stock
mechanism can do it: `TRANSPOSE_WORDS` needs one rule per word pair and only swaps positions,
`FOOD_REPLACE` is a regex but runs *after* the food/note split inside `parse_food` and can
therefore never write the note, and nothing at all applies to the raw line.

Putting the adjective in the note rather than in the food is what makes the aliasing question
mostly evaporate: `reif` rides on the ingredient row, so there is one `Avocado` food, not two
that need linking. Aliases are then only needed for genuine variants — `Avocados`/`Avocado`,
`EL`/`El`, `TL`/`Tl`/`tl`, `Msp.`/`Msp`.

A prototype over real corpus lines confirmed the mechanism and found the case that breaks the
naive version: **a line can carry only one note.** `parse_food` prefers a trailing
parenthetical and never consults the comma when one is present, so appending `, groß` to
`1 großer Becher Joghurt (500 ml)` yields the food `Joghurt, groß` with a comma inside its
name. The modifier has to be merged *into* the existing note, not added beside it. Ranges
collide the same way: `1 – 2 Eier (pro Person)` already has a parenthetical, and normalising
the dash without accounting for it produces the food `(pro Person)`.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | The rewrite lives in **the Word importer**, not in the shared `IngredientParser` | The alternative — a new automation type applied to the raw line — would touch `models.py`, a migration, the serializer, the frontend automation editor and the parser. That is real core divergence against REQ-001 Decision 5, for a problem that is entirely this collection's. The importer already owns the raw line and is already fork-local |
| 2 | Repairs are an **explicit list of concrete strings**, never inferred rules | No German morphology, no adjective-ending heuristics, no "looks like a unit" scoring. A rule that guesses is a rule that guesses *wrong* on the one line nobody checked. The corpus is finite and already measured: enumerate what is actually there |
| 3 | The list is **one committed file** beside the importer, not Automation rows in the database | Decision 8 restores the pre-import dump before re-importing, and a restore rolls the whole database back — Automation rows created after the dump would be silently wiped, so every re-import would need them re-created first or would quietly produce the old result. A file ships in the image and cannot get out of step with the code that reads it |
| 4 | A matched modifier is **merged into the line's existing note** when it has one, and appended as a new `, note` when it does not | `parse_food` prefers a trailing parenthetical and never consults the comma when one is present. Appending a second note puts a comma inside the food name — the exact fragmentation this REQ exists to remove |
| 5 | Repairs apply **only to the Word importer**, not to URL import or manual entry | Those paths are not where the collection comes from, and making the repairs global would mean the shared parser again (Decision 1). Recorded so the asymmetry is deliberate rather than discovered |
| 6 | The repair list is **produced by running the corpus**, and the run is a develop-session obligation | The list is an empirical object — its entries are exactly the strings 342 real documents produced. It cannot be written at a desk, and the System Tester can neither produce it nor fix what producing it reveals |
| 7 | Unit and food **aliases** (`EL`→`El`, `Avocados`→`Avocado`) live in the same file and are applied by the importer after parsing | Stock `UNIT_ALIAS`/`FOOD_ALIAS` automations would do this, but they are database rows and lose to Decision 3's restore for the same reason. One file, one place to look |
| 8 | The existing data is fixed by **restoring the pre-import dump and re-importing**, not by merging in place | The dump from REQ-006's deploy is on disk and verified restorable. A clean re-run is reproducible and repairs every row; merging afterwards cannot recover a note that was never parsed. Cost: instance edits made after the import are lost, which is accepted |
| 9 | The **ten table-shaped Chefkoch documents are never imported** | Reaffirmed by the owner at intake. This closes REQ-006's "known gap" as *declined*, not deferred: no follow-on REQ, no second parser profile, and the operator's zip excludes them permanently |
| 10 | Foods that legitimately begin with a digit — `1050er Weizenmehl`, `405er Weizenmehl`, `4%ige Natronlauge` — are **left alone** | They looked like parse residue in the first survey and are not: that is the flour's name. A repair list that "fixed" them would be inventing damage |

## Requirement

Ingredient lines in the household's Word documents are parsed into the shape their author
meant, and the deployed instance holds the result.

### The repair file

A committed file beside `cookbook/integration/word.py` holds the whole repair list, in four
sections, each an explicit mapping — no patterns that match anything not listed:

- **note modifiers** — surface form to note form (`reife` → `reif`, `gehäufter` → `gehäuft`,
  `altes` → `alt`). Every entry was observed in the collection.
- **unit aliases** — `EL` → `El`, `TL` → `Tl`, `tl` → `Tl`, `Msp.` → `Msp`, `Dosen` → `Dose`.
- **food aliases** — `Avocados` → `Avocado` and the other plural and spelling pairs.
- **range normalisation** — the en-dash forms the collection uses, so the parser's existing
  range handling fires.

### The rewrite

Before a raw ingredient line reaches `IngredientParser`, the Word importer:

- removes each listed modifier from the line and records its note form;
- normalises a listed range form;
- puts the recorded note forms into the line's **existing** parenthetical note when it has
  one, and appends them as `, <note>` when it does not;
- leaves any line containing nothing from the list **byte-identical**.

After parsing, listed unit and food aliases are applied, so an aliased pair resolves to a
single `Unit` or `Food` rather than two.

### The result

`1 reife Avocado` yields amount 1, no unit, food `Avocado`, note `reif`. `1 gehäufter Tl Senf`
yields amount 1, unit `Tl`, food `Senf`, note `gehäuft` — the real unit recovered from the
food name. No adjective from the list survives as a unit, and no listed alias pair survives as
two objects.

### The collection

The develop session runs the importer over the whole collection, builds the repair list from
what that turns up, and iterates until the yield is right. It then restores the pre-import
dump on the deployed host and re-imports, so the live instance holds the repaired result
rather than the REQ-006 one.

## Notes

**Sequencing — REQ-006's validation must run first.** REQ-006's AC5 is graded against the
import that is live now (`Import 5`, 270 recipes, three named recipes recorded in
`.devsteward/evidence/REQ-006/import-source.json`). Decision 8 restores the database and
re-imports, which changes the keyword and the counts and would leave that evidence describing
a state that no longer exists. Run `steward validate REQ-006` **before** starting this REQ's
develop step. The `depends_on: REQ-006` above enforces the ordering mechanically — REQ-007's
develop step is not eligible until REQ-006 is done.

**Required environment.** AC1-AC4 need only what a clean checkout has: pytest-django against
SQLite, plus the `python-docx` dependency REQ-006 added. None of them can pass by skipping.
The fixtures are written for the tests and mirror the collection's conventions; no document
from the real collection is committed, and no real ingredient line is asserted against in the
gate. AC5's evidence records real ingredient lines, which the owner has agreed to.

**What this does not fix.** The 17 nouns pressed into service as units (`Zitrone`, `Stück`,
`Stange`) are left alone: several are legitimate units in a kitchen, and separating those from
the mistakes needs a judgement this REQ has no basis to make. The long tail of foods used
exactly once is reduced by the repairs but not eliminated — descriptive names like
`geräucherter durchwachsener Speck` are how the recipes are actually written, and normalising
them is curation of the household's own words, not a parsing fix. Neither is a defect being
deferred; both are out of scope by choice, and the repair file can absorb either later without
a code change.

**Chefkoch documents.** Declined permanently (Decision 9). REQ-006's plan recorded them as a
gap to be closed by re-saving them in Word; that is superseded here. They are excluded from
the import zip and no acceptance criterion mentions them.

**Upstream.** Not offered, for the same reason as REQ-006: the repair list encodes one
household's German ingredient vocabulary, and the mechanism lives in an importer that is
itself fork-local. The rejected alternative — a new automation type on the shared parser —
*would* have been upstream-shaped, and is recorded in Decision 1 in case that trade ever looks
different.
