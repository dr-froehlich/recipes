## Context

Tandoor stores and displays every recipe and step duration as a flat number of minutes. A
72-hour sourdough proof renders as **`4320 min`**, which no cook reads as three days.
Upstream issue [#382](https://github.com/TandoorRecipes/recipes/issues/382) asked for this
on 2021-02-03; the maintainer agreed the same day ("everything over 60 minutes is
converted to hours and minutes"), a contributor sketched a `timeConvert()` helper in the
thread, mentoring time ran out, and the issue has been **open and unimplemented ever
since** — five and a half years, five thumbs-up, no PR.

**This REQ exists because that history is easy to misread.** PRs
[#3751](https://github.com/TandoorRecipes/recipes/pull/3751) (closed) and
[#3778](https://github.com/TandoorRecipes/recipes/pull/3778) (merged 2025-07-06, shipped
in 2.6.12/2.6.13) are cited under #382 and look like the fix. They are not. Together they
are 20 lines in `vue3/src/components/display/Timer.vue`, adding a localized `+2 Days`
suffix to the **running step timer's** "Finished at" line when the countdown crosses
midnight. That code is already present in this fork and is *working correctly* — it is
simply almost never visible, because it requires a step with a time, a timer the user has
actually started, and a finish that lands on a later calendar day. Nothing is disabled and
there is nothing to switch on. The feature #382 asked for was never built.

Today's raw-minute surfaces, all read-only display:

| Surface | Location | Renders |
|---|---|---|
| Recipe detail, layout A | `RecipeView.vue:43,47` | `4320 min` — working and waiting time, with a **hardcoded** `min` that bypasses i18n |
| Recipe detail, layout B | `RecipeView.vue:98,102` | `4320 {{$t('min')}}` — same values, localized |
| Recipe card chip | `RecipeCard.vue:32` | `4335` — working + waiting summed, with **no unit at all** |
| Step timer button | `StepView.vue:12` | `4320` — the least readable number in the app |

The recipe card is reused by the meal-plan and horizontal recipe windows, so fixing it
covers those. The *editors* (`RecipeEditor`, `StepEditor`, `BatchEditRecipeDialog`) keep
plain minute inputs — entering durations is not the problem, reading them is.

Two things make this cheap. `use_fractions` is an exact precedent for a per-user display
preference and runs end to end through the codebase: `models.py:529` (BooleanField) →
`serializer.py:580` → a pure helper in `utils/number_utils.ts` → a checkbox in
`CosmeticSettings.vue:33` → read at call sites via
`useUserPreferenceStore().userSettings.useFractions`. And PR #3778 already added the
`Hour`/`Hours`/`Day`/`Days` translation keys alongside the existing `min`, in English and
German.

One thing makes it awkward: **`vue3/` has no test runner.** `package.json` has `dev`,
`build`, `preview` and nothing else; there are zero spec files; CLAUDE.md states plainly
that vue3 changes are verified manually. The duration formatter is a pure function of one
number and a boolean — the single most testable thing this fork will ever contain — and
there is currently no way to test it.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Format rule: below 60 minutes render minutes; at or above 60 render `H h`, plus ` M min` when the remainder is non-zero. **No day rollover** — 4320 stays `72 h` | Matches the maintainer's stated expectation in #382, so the change remains offerable upstream. Days are deliberately not used: the running timer already expresses "+3 Days" for the one case where a calendar day matters, and proofing times are spoken as "72 hours", not "3 days". `#382`'s own table also keeps 4320 as hours |
| 2 | A per-user boolean preference `use_readable_time`, mirroring `use_fractions` field-for-field | It is a worn seam — one migration, one serializer entry, one checkbox — not new machinery, and it lets any household account opt back out without a code change |
| 3 | The preference defaults **ON** | REQ-001 Decision 1: the fork serves this household first. A display improvement gated behind a setting nobody knows to look for is not delivered. Noted as the one choice to revisit if this is ever offered upstream, which conventionally defaults new display preferences to the old behaviour |
| 4 | Introduce **vitest** as a dev-only devDependency plus a `test` script | Without it, the one deterministic, exhaustively-checkable piece of this REQ would be validated by a human squinting at a page, and every later regression would be silent. Vitest is Vite-native so configuration is near-zero, and being dev-only it cannot reach the shipped bundle. It also makes every future vue3 REQ in this fork testable |
| 5 | The conversion lives in one shared util module and is called from each display site; no duplication, and no per-component reimplementation | Keeps the diff small, reviewable and rebase-clean (REQ-001 Decision 2), and is the shape upstream asked for in the #382 thread |
| 6 | No server-side formatting and no API change beyond the preference field | Duration formatting is a display concern. Round-tripping it through the API would need serializer work and a client regeneration for no benefit, and upstream would reject it |
| 7 | Fix the hardcoded `min` at `RecipeView.vue:43,47` while touching those lines | It is a live i18n defect on the exact lines this REQ rewrites. Leaving it would mean knowingly shipping an untranslatable string in a REQ whose whole subject is how those strings render |

## Requirement

Recipe and step durations are shown in a form a cook can read, everywhere they are
displayed, controllable per user.

### The formatter

A shared utility converts a duration in minutes to a display string:

| Input | Output |
|---|---|
| 45 | `45 min` |
| 59 | `59 min` |
| 60 | `1 h` |
| 90 | `1 h 30 min` |
| 120 | `2 h` |
| 150 | `2 h 30 min` |
| 4320 | `72 h` |
| 0, null, undefined | rendered exactly as the call site renders them today |

Unit labels come from the existing translation keys, so a German user sees `2 Std 30 min`
if and when those keys carry a German short form — no unit string is inlined in logic.
With the preference **off**, the utility returns today's raw-minute rendering unchanged.

### The preference

`UserPreference.use_readable_time`, a boolean defaulting to `True`, exposed through the
user-preference API, surfaced as a checkbox in Cosmetic settings next to "Use fractions",
and read at each call site from the user-preference store. Because the serializer changes,
the generated OpenAPI TypeScript client must be regenerated — an un-regenerated client
means the frontend cannot see the field and the feature silently does nothing.

### The surfaces

The formatter is applied at every read-only duration display: both `RecipeView` layouts
(working and waiting time), the `RecipeCard` time chip — which must also gain a unit,
since it currently prints a bare number — the `StepView` timer button, and any further
read-only recipe or step duration found during the sweep. Duration *inputs* keep plain
minutes.

## Notes

**Required environment (AC1).** The vitest run needs the vue3 toolchain: **Node ≥ 20.19**
(vite 8 will not run on older) and **yarn**, with `yarn install` having been run in
`vue3/`. The workstation currently has Node 18.19.1, no yarn on PATH, and no
`vue3/node_modules` — installing that toolchain is part of this REQ's develop work, and
the AC will hard-fail rather than silently skip until it is done. AC2 and AC3 are
self-contained against a clean checkout with the project venv.

**Why AC4 is `manual` and not deferred iteration.** The formatter's real risk is
exhaustively covered by AC1 against a synthetic table — there is no production corpus that
can surprise a pure function of one integer. What AC4 checks is *wiring*: that the
preference actually reaches four call sites in a built bundle served to a browser. That
needs a human oracle but no fixing loop, so the System-Test phase is the right home.

**Scope boundaries.** Duration *entry* stays in minutes across all editors. The API
continues to serve integers. The `Timer.vue` countdown (`hh:mm:ss`) and its `+Xd` finish
suffix are already correct and are not touched. Fractional/decimal-hour rendering
(`1,5 h`), the alternative floated in #382, is rejected by Decision 1 and is not a hidden
option.

**Upstream.** Offering this to #382 is explicitly *not* part of this REQ (REQ-001
Decision 3) — it would make completion depend on a maintainer's review queue. Decisions 1,
5 and 6 keep the diff in a shape that could be offered later; Decision 3 is the one point
upstream would likely want changed.
