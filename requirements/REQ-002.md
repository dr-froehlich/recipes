## Context

REQ-001 says this fork exists to *run* Tandoor for the owner's household. Today it cannot:
the household host runs the **published upstream image**, pinned by release tag, via a
three-service `docker compose` stack (app + PostgreSQL 16 + a reverse proxy terminating
TLS). Nothing on that host builds from source, so no local change — however well tested —
can ever be seen by a user. Every feature REQ in this fork is blocked on the same missing
capability, which is why it is its own REQ rather than a tail appended to the first
feature that needs it.

Three facts shape the solution.

**The host cannot build.** It is `aarch64` with 4 cores, ~3 GB RAM (about 1 GB free) and a
root filesystem at 88 % capacity, while serving a dozen other containers including a
password manager and the household's DNS. The `Dockerfile` compiles `cryptography` and
`setuptools_rust` from source under a `gcc`/`cargo` build-deps layer. Running that on the
host risks OOM-killing production services and exhausting the disk.

**The workstation is the wrong architecture.** It is `x86_64`, so a local build for the
host means `buildx` + QEMU emulation of exactly those Rust compiles — tens of minutes to
hours per iteration, plus a ~1 GB image pushed over the LAN each time.

**Upstream already solved this, and the solution is one condition away from working.**
`.github/workflows/build-docker.yml` performs a `linux/amd64,linux/arm64` buildx build and
pushes to Docker Hub and ghcr.io. It is gated `if: github.repository_owner ==
'TandoorRecipes'`, so on a fork it silently skips — the workflow appears to run and
produces nothing. Adopting it costs a condition and an image name, not a new pipeline.

One non-obvious build ordering matters: the Vue 3 SPA is built **outside** Docker. The
workflow runs `yarn install && yarn build` in `vue3/`, which emits into
`cookbook/static/vue3/` — a **gitignored** directory — and only then does the image's
`COPY . ./` pick the assets up. A Docker build that skips the yarn step produces an image
that starts cleanly and serves **no frontend at all**. Any deploy path must preserve that
ordering.

Finally, the household database is the household's only copy: `./postgresql` is a bind
mount with no backup mechanism in place. Feature REQs will ship migrations against it.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Build in GitHub Actions on the fork, publish to `ghcr.io/dr-froehlich/recipes` | Free cross-architecture build, zero load on a memory- and disk-constrained production host, and reproducible from a commit sha rather than from whatever was in someone's working tree |
| 2 | Relax upstream's owner gate and add the fork's image name; do not rewrite the workflow | REQ-001 Decision 5 — take the cheap seam. A minimal diff to `build-docker.yml` stays reviewable and re-appliable across upstream rebases; a rewritten workflow would conflict on every upstream CI change |
| 3 | The fork repository stays public, and REQ files stay sanitized | Keeps the option of offering an individual change upstream (REQ-001 Decision 3) without publishing the household's LAN hostname, internal IP, public recipe domain, or which services share the box. Concrete deploy targets live in a gitignored `deploy/target.env`; REQs and committed docs refer to them by name only |
| 4 | No migration runs behind an unverified backup | The bind-mounted database has no backup regime. The deploy pre-flight takes a dump and proves it is *restorable* — a dump that was never checked is not a restore point. This is a gate on the deploy, not a standing backup regime |
| 5 | Publishing is driven by pushes to `develop`; images are addressed by commit sha | The sha is the only identifier that cannot drift. A moving `develop` tag is a convenience; the sha is what the sign-off checks |
| 6 | The upstream-rebase workflow is **out of scope** and is homed in a named follow-on REQ | Tracking a future upstream release is a distinct problem (conflict handling, re-testing every local REQ) and cannot be proven until upstream ships a release worth taking. Deferring it here is explicit, not silent |
| 7 | The live deploy is performed and iterated **inside the attended develop session** | Registry visibility, ghcr authentication, the arm64 build, compose changes and the migration will need several rounds against the real host. The System-Test phase runs in a session that cannot fix anything, so routing that iteration there would bounce a red back a whole session later. AC4 signs off a deployment that already works |
| 8 | `develop: split` — an attended design review precedes the build | This REQ's build phase mutates a production host and its only database. The design of the deploy procedure is reviewed with the owner before anything touches the host |

## Requirement

The fork can be built and run on the household host, repeatably and without risking the
database.

### Build

A push to `develop` on `dr-froehlich/recipes` produces a `linux/arm64` image published to
`ghcr.io/dr-froehlich/recipes`, tagged with both the branch name and the commit sha, with
the Vue 3 SPA built into it. The workflow reaches this by the smallest possible change to
upstream's `build-docker.yml`: admitting the fork's owner and adding the fork's image
name. The package is published so the host can pull it without registry credentials.

### Deploy

A committed, repeatable procedure — a script plus a short docs page — takes the host from
the currently-running image to a named fork image. It must, in this order:

1. Read its target (host, compose directory, public URL) from the **gitignored**
   `deploy/target.env`; refuse to run if that file is absent. No host, path, IP or domain
   is committed.
2. Take a `pg_dump` of the live database and **verify the dump is restorable**. If
   verification fails, stop before anything else changes.
3. Point the compose stack at the fork image by sha and bring it up.
4. Run migrations.
5. Report the version the host is now running.

### Observable result

The live site serves the fork's image, and this is checkable rather than asserted: the
Django system page reports the commit hash and branch baked in at image build time by
`version.py`, so an upstream release tag appearing there means the deploy did not take.

## Notes

**Fork remote.** `dr-froehlich/recipes` already exists (a public fork of
`TandoorRecipes/recipes`, default branch `develop`). This clone's `origin` still points at
**upstream**; part of this REQ is wiring the remotes so `develop` pushes to the fork and
upstream stays fetch-only. REQ-001's Notes anticipated exactly this.

**Out of scope, deliberately.** Pulling in future upstream releases (the rebase-onto-
upstream-`develop` workflow) is **not** covered here — Decision 6. Home: a follow-on REQ to
be intaken when upstream ships a release worth taking. A standing/scheduled backup regime
is also out of scope; Decision 4 gates the deploy only. Neither is a defect being deferred
silently — both are named here.

**Required environment.** AC1 and AC2 are self-contained: they parse a committed workflow
file and exercise the dump verifier against a synthetic file. AC2 needs the `pg_restore`
binary on PATH (present on the workstation, no server required). AC3 and AC4 need network
access to ghcr.io and SSH access to the household host, which is why they are `artifact`
and `manual` rather than `regression`.

**Risk.** The largest is registry visibility interacting with the pull: if the ghcr
package is published private the host needs a `docker login` with a read-scoped token,
which contradicts Decision 1's "no credentials on the host". The develop session confirms
the package is public before the deploy step. *Resolved during develop: the package
published **public**, and the host pulled it anonymously with no `docker login`.*

**Corrected premise (observed 2026-08-06, during the develop session).** The Context above
states the host has "~3 GB RAM (about 1 GB free) and a root filesystem at 88 % capacity".
Measured on the host: **3.7 GiB total with 2.6 GiB available**, and while the root
filesystem is indeed at 88 %, that is **61 GB free** in absolute terms. The percentage is
alarming; the absolute figures are not. This does not change the delivered design — the
dump is still streamed to the workstation and verification is still serverless, both of
which remain the right call for a routine pre-flight — but it does mean the constraint was
overstated as a *justification*. Concretely, it wrongly implies a second temporary stack is
unaffordable: one was run alongside production during this session at no observable cost,
and restoring the dump into it is what upgraded Decision 4's serverless check into a
demonstrated restore. A future REQ weighing work against these limits should use the
measured numbers, not this document's original ones.
