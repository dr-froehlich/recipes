## Context

The household's recipe collection does not live in Tandoor. It lives in **342 Word
documents** on a Syncthing share, written over years and still being written today — 23
category folders (`Fleisch`, `Nudelgerichte`, `Salziges Backen`, …), each recipe usually
paired with a printed PDF, 443 photographs embedded inside the documents themselves. That
collection is the reason this fork exists at all; the deployed instance currently holds a
handful of recipes while the real corpus sits in a folder tree nobody can search, scale,
or put on a shopping list.

Word is not a legacy format here — it is the **ongoing authoring format**. New recipes keep
arriving as `.docx`. That single fact rules out a one-shot conversion script: whatever is
built has to still work in a year, from the normal Import screen, without a developer in
the loop. Tandoor already has the shape for that — 23 `Integration` subclasses dispatched
by `get_integration()` in `cookbook/views/import_export.py`, everything from Paprika to
RezKonv — and none of them read Word.

Exploration established that this is unusually tractable, because the documents are not
free-form prose. They are **styled** with near-perfect consistency:

| Signal | Coverage |
|---|---|
| `Titel` paragraph style → recipe name | 311 / 342 |
| `Überschrift1` sections "Zutaten" / "Zubereitung" | ~310 |
| Bulleted `Listenabsatz` paragraphs → ingredients | 2745 lines |
| Plain body paragraphs → instruction steps | 2187 |
| Embedded photograph | 233 documents |

The decisive measurement: Tandoor's **existing** `IngredientParser` was run over all 2759
real ingredient lines and parsed **99.7%** correctly — `375 g Weizenmehl (550er)` →
`(375.0, 'g', 'Weizenmehl', '550er')` — including German units (`Tl`, `El`, `Prise`,
`Päckchen`, `Würfel`) and vulgar fractions (`½`, `1/8 l`). The seven failures are
instruction paragraphs that were accidentally bulleted in Word. So the hard, linguistic
half of the problem is already solved inside the codebase; what is missing is the
structural half — turning styled XML into a name, an ingredient list and an ordered set of
steps.

Two cheap seams make the diff small. The import type list the frontend renders is a
**hand-maintained TypeScript array** (`vue3/src/utils/integration_utils.ts`), *not* part of
the generated OpenAPI client — so adding a format needs **no client regeneration**, and
this REQ never goes near the ~40-plugin-file trap CLAUDE.md documents. And `Integration`
already provides zip unpacking, `import_recipe_image`, duplicate handling and the
auto-created `Import N` keyword, so a subclass inherits nearly all of the plumbing.

What is genuinely awkward is the tail. About **16 documents** were pasted from Chefkoch and
invert the convention exactly — no `Titel` at all, ingredients in a two-column **table**,
instructions as a **bulleted list**. Feeding those through the canonical parser would
produce recipes whose ingredients are instructions. Another ~20 files are not recipes:
empty `Allg. Vorlage Rind.docx` templates, `Rezeptecover*.docx`, and the `Ausgewählte
Bilder/` + `Food-Fotografie/` folders which re-copy recipes for photo work, producing 13
filename collisions.

The risk in this REQ is **corpus-shaped**, and that shapes the process. The failures that
matter are the ones only 342 real documents contain; no synthetic fixture invents them. The
System-Test phase runs in a fresh session that never sees the diff and cannot fix anything,
so routing the corpus proof there would turn every surprise into a whole extra session of
rework. Decision 9 therefore keeps the live corpus run inside the attended develop session,
where it can be fixed in place, and leaves the gate a mechanism proof against committed
synthetic fixtures.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | A **`Word` Integration subclass**, reachable from the normal Import screen — not a conversion script | Word stays the authoring format, so the value is in the path that still works next year without a developer. A script would be thrown away the day it finished running |
| 2 | Parsing is split into a **pure `.docx` → dict parser** and a thin Integration that maps the dict onto models | The parser is then testable without a database, and runnable standalone over the real corpus during develop — which is exactly what Decision 9 needs. It also keeps the household's Word conventions out of the model-writing code |
| 3 | Ingredient lines go through the **existing `IngredientParser`**; this REQ writes no ingredient grammar | It already parses 99.7% of the real corpus including German units and fractions. Writing a second parser would be strictly worse and would drift from the one the rest of Tandoor uses |
| 4 | **One Tandoor Step per Word paragraph**, ingredients attached to the first step | Gives REQ-004's bake schedule real per-step structure to back-chain over — a single merged step would leave it nothing to work with — and reads better on a phone in the kitchen than a wall of text |
| 5 | Repeated `Zutaten für X` sections become **named Steps** carrying their own ingredients, followed by that component's instructions | `Step.name` exists for exactly this. Merging Teig and Füllung ingredients into one list destroys information the document took the trouble to record |
| 6 | Only the **canonical style profile** is parsed. Table-shaped documents are **skipped and named in the import log**, never guessed at | The Chefkoch layout is inverted, not merely different — misparsing it yields recipes whose ingredient list is the method. Skipping is honest; the ~16 are homed in Notes, not silently dropped |
| 7 | A document yielding **zero ingredients and zero steps is skipped** with a log line. Folder exclusions and duplicate curation are the **operator's**, done when building the zip | The empty-document rule is general and belongs in code. "Ignore `Food-Fotografie/`" is one household's folder naming and belongs nowhere near the fork, per REQ-001 Decision 5 |
| 8 | **Top-level folder → keyword**, with the `Ausgedruckte Rezepte mit/ohne Bild` subfolders collapsed away | The 23 top folders are a real taxonomy worth 300 recipes of tagging. The print subfolders are a workflow distinction and would pollute the keyword tree with a concept that means nothing inside Tandoor |
| 9 | The **full-corpus run is a develop-session obligation**, not an acceptance criterion routed to validation | The System Tester cannot fix what it finds. The corpus is where the surprises are, so the iteration loop has to be attended and in-place. The gate instead gets synthetic fixtures proving the mechanism disconfirmably |
| 10 | The bulk import runs **once, behind a verified restorable dump** from REQ-002's deploy pre-flight | The dump *is* the rollback: a wrong yield is undone by restoring and re-running. This needs no new machinery — REQ-002 already proves its dumps restorable rather than merely taking them |
| 11 | **First embedded photo becomes the recipe image; the rest are discarded** | Matches every existing Tandoor importer. Anchoring step photos to steps would add `UserFile` creation and quota handling for images that remain safe in the original documents |

## Requirement

A `.docx` recipe, or a zip of them, can be imported through Tandoor's normal Import screen,
and the household's existing collection is actually in the deployed instance when this is
done.

### The parser

A pure function takes `.docx` bytes and returns a structured recipe, or reports why it
cannot:

- **Name** from the `Titel`-styled paragraph.
- **Servings** from the ingredient heading's trailing text — `Zutaten für 4 Personen` and
  `Zutaten für sechs Brezeln (ein Blech)` both yield a servings count and a servings text.
  Digits and German number words both resolve to the integer; anything unresolvable leaves
  the count at its default and keeps the phrase as text.
- **Ingredients** from bulleted paragraphs under a `Zutaten` heading, one raw line each,
  left for `IngredientParser` to split into amount, unit, food and note.
- **Steps** from the body paragraphs under a `Zubereitung` heading, one step per paragraph,
  in document order.
- **Components**: each further `Zutaten für X` heading opens a new named step carrying its
  own ingredients and its own following instructions.
- **Image**: the first embedded photograph, as bytes plus its file type.

A document is reported **unparseable** — never guessed at — when it contains a table in
place of a bulleted ingredient list, and **empty** when it yields no ingredients and no
steps at all.

### The integration

A `Word` integration registered under a `WORD` type, reachable through the same three
places every other format is: the dispatcher in `cookbook/views/import_export.py`, the
choice list in `cookbook/forms.py`, and the frontend registry in
`vue3/src/utils/integration_utils.ts`. It accepts a single `.docx` and a `.zip` containing
many.

For each parsed document it creates a Recipe in the requesting user's space with its
ingredients resolved to `Food` and `Unit` through `IngredientParser`, its steps in order,
its image attached, the auto-created `Import N` keyword, and a keyword named for the
**top-level folder** the document sat in inside the zip — with any `Ausgedruckte Rezepte
mit Bild` / `… ohne Bild` level collapsed away.

Skipped documents are named in the import log with the reason, and never abort the run: a
zip containing unparseable, empty and valid documents imports the valid ones.

### The corpus

The develop session runs the parser over all 342 real documents, iterates on what that
turns up until the yield is right, and records the outcome per file. It then deploys the
fork and performs the bulk import into the live instance behind a verified restorable dump.
When this REQ is done the household's recipes — on the order of 300 of them, with
ingredients, ordered steps, a category keyword and a photograph where one existed — are in
Tandoor on the deployed server, not in a folder tree.

## Notes

**Required environment (AC1–AC4).** `python-docx` becomes a project dependency and is added
to `requirements.txt`; it is already installed in `.venv`. The criteria otherwise need only
what a clean checkout has — pytest-django against SQLite — so none of them can pass by
skipping. The fixtures under `cookbook/tests/other/test_data/Word/` are **written for the
tests**, mirroring the household's conventions; no document from the real collection is
committed, so the gate never asserts against production content.

**Why the corpus proof is a develop obligation and not an acceptance criterion**
(Decision 9). AC1–AC4 prove the *mechanism* against fixtures whose expected output is known
by construction. What they cannot prove is *yield* — how many of 342 real documents come
through intact, and what the tail looks like. That question is only answerable by running
it, and answering it produces fixes. Since the System Tester never sees the diff and cannot
fix anything, routing it there would convert every discovery into a session of rework. AC5
grades the settled outcome afterwards, which needs a human oracle but no fixing loop.

**Known gap, homed not deferred (Decision 6).** The ~16 table-shaped documents pasted from
Chefkoch are skipped, not imported. Two remedies exist and the develop session's corpus run
decides which is worth it: re-save them in Word to the household's own convention, which
costs no code and improves the source of truth; or a follow-on REQ adding a second parser
profile that reads ingredients from a two-column table and steps from a bulleted list. The
count is small enough that the first is likely to win, but the choice is deliberate and
recorded either way.

**Scope boundaries.** No model, migration or serializer change, and therefore no OpenAPI
client regeneration — the frontend import registry is a hand-maintained array. No `.doc`
support (there is exactly one in the collection). No export back to Word. Step photographs
beyond the first are discarded (Decision 11). The importer does not deduplicate by recipe
name, does not exclude folders by name, and knows nothing about `Food-Fotografie` or
`Rezeptecover` — curating the zip is the operator's job (Decision 7). The 433 companion
PDFs are ignored. Nothing reads the collection path from inside the application; the corpus
location is a develop-session input, not configuration.

**Upstream.** Deliberately not offered (Decision 12), unlike REQ-003/REQ-005. The parser
encodes one household's Word conventions and the feature would push `python-docx` onto
every upstream install. The touch points are kept to one new integration file plus four
small edits — dispatcher, form choices, frontend registry, requirements — so the fork stays
legible across rebases and other changes remain offerable on their own merits.
