## Context

This fork's test suite has never run in GitHub Actions. Not once, on any commit.

`.github/workflows/ci.yml:7` carries `if: github.repository_owner == 'TandoorRecipes'` at job
level. On a fork that condition is false, so the job is skipped: the run appears in the checks
list, reports **success**, and executes nothing. It is the same silent no-op REQ-002 found in
`build-docker.yml` — a workflow that looks green because it did not run. REQ-002 removed that
one gate because an image had to exist; the identical gate on the test workflow was left in
place, and nobody noticed because a skipped run is not a failed run.

It surfaced on REQ-008's develop session: the commit that added a Django model field, a
migration, four serializer changes and a regenerated API client produced three GitHub check
runs — `Build Docker Container` success, `Continuous Integration` **skipped**, `Code scanning`
**skipped**. Two of the three had never had an opinion about anything this fork has ever
written.

**Nothing has shipped unverified.** DevSteward's land gate runs the full suite locally
(`verify.full_suite` in `.devsteward/config.yaml`) and refuses to close a checkpoint on red, so
every commit that reached `develop` through `/advance` passed the suite on this workstation.
What is missing is everything a clean-environment run catches that a warm working tree does not:
a file that was never committed, a dependency missing from `requirements.txt`, a build step that
only works because an artifact from a previous run is still lying around. And a push that
bypasses `steward` has no check at all.

Three workflows carry the gate — `ci.yml:7`, `codeql-analysis.yml:11`, `docs.yml:12` — and all
three are ungated here.

**The PostgreSQL gap this closes.** REQ-001's Notes record a deferred defect verbatim: *"the
suite defaults to SQLite, so 18 search tests marked `requires PostgreSQL` never execute locally,
while production runs PostgreSQL 16 … Closing that gap means running the suite against
PostgreSQL via the `TEST_*` env vars — an environment-bound concern that should not be attached
to the north star's own acceptance. Home: a follow-on REQ."* Nothing has claimed it since. CI
with a service container is the natural home, and it is the one thing CI can offer that the
local land gate structurally cannot. Those 18 tests (`requires_postgres` in
`cookbook/tests/other/conftest.py:23`) have therefore **never executed anywhere** — not locally,
not upstream-for-this-fork, not in any deploy. They may well be red on first run. That is the
point, and it is the main risk this REQ carries.

`vue3`'s vitest suite has a narrower version of the same problem: it runs in the land gate only
when a REQ names it as an acceptance criterion. REQ-003, REQ-004 and REQ-008 each do, but a
future REQ that breaks it without naming it would land green.

**What ungating `docs.yml` costs, found at intake.** `docs/CNAME` contains `docs.tandoor.dev`,
upstream's verified custom domain. `mkdocs gh-deploy --force` writes that file into the deployed
branch, so an ungated docs workflow would have this fork's GitHub Pages attempt to claim a domain
it does not own. Two things keep this from being urgent: the workflow fires on `workflow_run` of
CI restricted to `branches: [master]`, and this fork never commits to `master` (CLAUDE.md), so it
is dormant until the first release; and `docs/reports/` is gitignored, so the pytest HTML report
is not among the published files. Dormant is not fixed, so the CNAME is dealt with here.

## Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Remove the job-level owner gate from **all three** workflows — `ci.yml`, `codeql-analysis.yml`, `docs.yml` | They are one defect in three files: a check the fork inherited and that has never once run here. Fixing only the one that prompted this would leave the same trap for whoever next reads a green checks list |
| 2 | The **remaining** owner gates in `build-docker.yml` stay exactly as REQ-002 left them | Those guard things that genuinely are upstream-only — the Docker Hub login (`:58`), the `vabene1111/recipes` image name (`:76`), and the tag and beta publish jobs (`:105`, `:123`). They are not the same defect and removing them would break the fork's build, not fix it |
| 3 | `ci.yml` gains a **PostgreSQL 16 service container** and passes the `TEST_*` env into pytest, so the 18 `requires_postgres` tests execute | REQ-001's Notes home this gap in a follow-on REQ and this is it. Production runs PostgreSQL 16 while every test to date has run on SQLite; CLAUDE.md already warns that Search and Food behaviour differs between the two. This is the one check CI can make that the local land gate structurally cannot |
| 4 | `ci.yml` also runs `yarn --cwd vue3 test` unconditionally | Otherwise the frontend suite is only ever exercised by whichever REQ happens to name it, which makes its coverage a property of REQ authorship rather than of the codebase |
| 5 | **No flake8 step.** The lint gap is named as a follow-on REQ, not fixed here | `flake8 --ignore=E501` reports many violations in upstream code this fork has not touched (`serializer.py`, `views/api.py`), so a lint step would be red from day one. Making it green means deciding what to do about inherited violations — a scoping decision that deserves its own REQ rather than being smuggled into this one |
| 6 | CI stays **advisory**: `deploy/deploy.sh` is not changed and a red CI does not block a deploy | The land gate already refuses to close a checkpoint on a red suite, so a commit reaching `develop` through the normal flow has passed. Coupling the deploy to the GitHub API would add a failure mode (and an escape hatch to go with it) for a case the land gate already covers. Revisit if a red CI ever does reach a deploy |
| 7 | `docs/CNAME` is changed so it no longer names upstream's domain; the fork publishes at its own `github.io` address | The alternative — leaving the CNAME and relying on GitHub Pages simply never being enabled — makes correctness a property of a repository setting nobody can see from the code, where enabling Pages later would claim someone else's domain with no warning. A one-line divergence that will reappear on every upstream rebase is the cheaper mistake |
| 8 | The proof that the workflows **run and pass** is a develop-session obligation, not an acceptance criterion routed to validation | Whether a workflow fires and goes green is only knowable by pushing and watching GitHub, and the 18 never-executed PostgreSQL tests are exactly the kind of thing that needs a fixing loop. The System Tester runs in a fresh session that never sees the diff and cannot fix anything (REQ-030), so a red there costs a whole session. Same shape as REQ-002 Decision 7 and REQ-008 Decision 10 |

## Requirement

The fork's own checks run in GitHub Actions on every push, against the database production
actually uses.

### The gates

No job in `.github/workflows/ci.yml`, `.github/workflows/codeql-analysis.yml` or
`.github/workflows/docs.yml` is conditioned on the repository owner. The owner conditions in
`build-docker.yml` that guard upstream-only credentials and publish targets are untouched.

`docs/CNAME` no longer names `docs.tandoor.dev`.

### What CI runs

`ci.yml`'s job, in addition to what it does today:

- A **PostgreSQL 16 service container**, with the `TEST_*` environment variables
  (`recipes/test_settings.py`) pointed at it, so `pytest` runs against PostgreSQL and the 18
  tests marked `requires_postgres` **execute** rather than skip.
- A step running the `vue3` vitest suite.

### The live proof

The develop session pushes and watches the run until `Continuous Integration` concludes
**success** on the fork, with the PostgreSQL tests executed and the vitest step run — fixing in
place whatever that first real execution turns up. A workflow that is present and correct in the
YAML but does not actually run, or runs red, does not satisfy this REQ.

```yaml acceptance
- id: AC1
  text: >
    No workflow the fork depends on is silently gated off. Parsing
    .github/workflows/ci.yml, codeql-analysis.yml and docs.yml, no job carries a condition on
    github.repository_owner. Parsing build-docker.yml, the four owner conditions that guard
    upstream-only credentials and publish targets are still present — the Docker Hub login, the
    upstream image name, the tag publish job and the beta publish job — so this REQ cannot pass
    by deleting every owner condition in the tree. docs/CNAME does not contain
    docs.tandoor.dev.
  test: 'python -m pytest cookbook/tests/other/test_ci_workflows.py::test_no_owner_gates --no-cov'
  check: regression
  status: pending

- id: AC2
  text: >
    The CI workflow declares the checks this REQ adds. Parsing .github/workflows/ci.yml, the
    job defines a service container running a postgres 16 image; the step that invokes pytest
    receives the TEST_* environment variables that recipes/test_settings.py reads, naming that
    service as the host; and some step invokes the vue3 vitest suite. Each is asserted
    individually, so removing any one of them fails.
  test: 'python -m pytest cookbook/tests/other/test_ci_workflows.py::test_ci_declares_postgres_and_vitest --no-cov'
  check: regression
  status: pending

- id: AC3
  text: >
    The workflow actually ran, against PostgreSQL, and passed — checked through the real
    entrypoint rather than from the configuration. For the commit under validation, the
    Continuous Integration workflow run on the fork concluded success and was not skipped; its
    captured junit results record the 18 tests marked requires PostgreSQL as executed, with
    none of them skipped for a missing database; and the run's log or step list shows the vitest
    step having run. Evidence is the run conclusion plus the junit XML the workflow already
    produces (--junitxml=junit/test-results-*.xml), captured into the evidence dir. A workflow
    that is correct in YAML but skipped, cancelled, or green only because the PostgreSQL tests
```

## Notes

**Process declarations, made at intake (2026-08-16).** `develop: fused`, `concept: false`,
`lab: []` — all defaults, so the `process:` block is omitted. The lab AC3 needs is GitHub Actions
itself, which already exists; no REQ needs to own a new asset.

**Required environment.** AC1 and AC2 parse files in the repository and need nothing but a
checkout — they are self-contained and cannot skip. AC3's oracle is a run on GitHub, captured as
evidence; it skips outside a validation, like the sign-off harnesses REQ-003, REQ-004 and REQ-008
already use.

**Shortening the develop loop.** The workstation has Docker and a PostgreSQL client, so the
develop session can spin an ephemeral PostgreSQL 16 container and run the 18 `requires_postgres`
tests locally via the `TEST_*` variables before pushing, rather than discovering each failure one
CI round-trip at a time. That is a convenience, not a substitute — Decision 8's obligation is
satisfied only by a green run on GitHub.

**The main risk, stated plainly.** The 18 PostgreSQL tests have never executed anywhere. If they
are substantially red, this REQ becomes a bug-fixing REQ of unknown size. Two honest outs if that
happens: fix them here if the failures are shallow, or land the CI wiring with the PostgreSQL leg
green-listed down to the subset that passes and home the remainder in a **named follow-on REQ**
— never by quietly reverting to SQLite, which would recreate exactly the gap this REQ exists to
close. Which of the two applies is a decision for the develop session, taken with the failures on
screen.

**Scope boundaries.** No flake8 or formatting step (Decision 5) — the lint gap is a named
follow-on REQ, to be intaken when someone is willing to decide about inherited violations.
`deploy/deploy.sh` is untouched and a red CI does not block a deploy (Decision 6). The workflows
are otherwise not rewritten: upstream's job structure, caching strategy and action versions stay
as they are, per REQ-001 Decision 5 and REQ-002 Decision 2, so this stays a small reviewable diff
across upstream rebases. Nothing is done about the fork's GitHub Pages site beyond making the
CNAME safe — whether to actually enable Pages is left open, and the site remains dormant until a
first `master` release regardless.

**Upstream.** The gate removals are owner-agnostic and would mean only "forks run their own
tests", so they are offerable upstream on their own merits (REQ-001 Decision 3); the PostgreSQL
leg and the vitest step plausibly are too. `docs/CNAME` is fork-specific by definition and never
goes upstream — it is a permanent one-line divergence and will conflict on rebases that touch it.
