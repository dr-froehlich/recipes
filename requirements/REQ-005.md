## Context

REQ-003 built human-readable durations for this household. This REQ offers that work to
upstream Tandoor as a pull request. It is the first time anything from this fork leaves the
machine under the owner's name, and the owner has never opened a pull request before — so
the mechanics, the project's rules and the netiquette are all part of what this REQ has to
get right, not background knowledge it can assume.

**The topology is already in place.** `origin` is `git@github.com:dr-froehlich/recipes.git`
— the owner's personal GitHub fork, push enabled. `upstream` is
`https://github.com/TandoorRecipes/recipes.git`, fetch-only, with push explicitly set to
`no_push`. A pull request is a request that upstream pull from a branch on the *personal
fork*; nothing is ever pushed to upstream. This corrects REQ-001's closing note, written
before the fork remote existed.

**The branch cannot come from `develop`.** Measured on 2026-08-12, this fork's `develop` is
**21 commits ahead of `upstream/develop` and 10 behind**. Those 21 commits are almost
entirely fork harness: the DevSteward ledger, REQ-001's north star, REQ-002's CI and deploy
work, REQ-004's intake, engine skill files, `STEWARD.md`, `deploy/`. Cutting a PR branch
from `develop` would drag all of it into the diff. The branch must be cut from a freshly
fetched `upstream/develop` with only the contribution replayed onto it.

**What the contribution actually is.** The upstream-shippable content of REQ-003 lives
entirely in commit `b00564cb0` plus the `vue3/package.json` test-script fix from
`ef7897d48`. Everything else across REQ-003's commits — `requirements/`, `.devsteward/`,
`.claude/`, `STEWARD.md`, `deploy/`, the `CLAUDE.md` edit, and
`cookbook/tests/other/test_readable_time_signoff.py` (a DevSteward evidence grader that
reads `DEVSTEWARD_EVIDENCE_DIR` and is meaningless outside this harness) — is fork harness
and must not ship.

**What upstream requires**, from `docs/contribute/guidelines.md` and
`docs/contribute/translations.md`:

| Requirement | Consequence here |
|---|---|
| A signed Contributor License Agreement (cla-assistant.io/TandoorRecipes/recipes) | A hard blocker; a bot enforces it on the PR. Tandoor is AGPL v3 **plus a Commons Clause** with a hosted commercial offering, which is why a CLA exists at all |
| flake8, yapf, isort on Python; prettier on Vue — "you are required to use" | A formatting gate the PR branch must pass, not a suggestion |
| "If you make any functional changes, please implement the appropriate tests" | REQ-003's API test ships; the vitest suite is the frontend half |
| Larger features need a technical description first | Scoped to features "that introduce more complexity". The same page opens with "bug fixes or small tweaks … are always welcome". A ~5-file change against an issue the maintainer agreed to in 2021 is the second case |
| Translations go through Weblate; direct PR translations "sometimes cause issues merging with weblate, so I would prefer the use of weblate" | The PR ships English keys in `en.json` only. Hand-writing 35 catalogs would be working against the maintainer's stated preference |

**The localization question that prompted this REQ.** REQ-003 minted three new keys, all
English-only: `Use_Readable_Time`, `Use_Readable_Time_Help` (the settings toggle label and
hint) and — a finding the owner did not ask about — **`h`**, the formatter's own hour unit,
which `git log -S` traces to `b00564cb0`. REQ-003's Context wrongly assumed `h` already
existed. `min` genuinely does, translated in all 36 locale files; `h` is translated in one.
With `i18n.ts:77` setting `fallbackLocale: 'en'`, the hour label falls back to English in
35 locales — a gap that is *more* exposed than the toggle, since it appears on every recipe
page, card and timer button. It reads correctly in German, French, Italian, Spanish and
Dutch, and wrongly in Japanese, Chinese, Russian, Greek, Hebrew and Arabic. Under upstream's
Weblate policy the correct contributor action for all three keys is identical and already
done: ship the English key, correctly named, and let Weblate propagate.

**One collision to watch.** This fork's migration is `0243_userpreference_use_readable_time`;
`upstream/develop` currently tops out at `0242_space_household_setup_completed`, so `0243`
is free *today*. Upstream is 10 commits ahead of us and may take it before the PR lands, so
the number has to be re-checked when the branch is cut, not assumed from this paragraph.

| 2 | The branch is **structured into separable commits** — the feature and preference first, the vitest introduction last — and the PR description names the seams | This is what makes Decision 1's offer credible. ## Requirement

REQ-003's work is offered to upstream Tandoor as a clean, reviewable pull request that
contains the contribution and nothing else, and the owner understands what was published
and why.

### The branch

A branch cut from a freshly fetched `upstream/develop`, carrying only the upstream-shippable
content of REQ-003 (`b00564cb0` plus the `vue3/package.json` test-script fix from
`ef7897d48`), replayed as **separable commits**:

1. the formatter, the preference (authored `default=False`), the migration, the serializer,
   the four display call sites, the settings checkbox, the `en.json` keys, the regenerated
   OpenAPI models, and the Python API test;
2. the vitest introduction — `vue3/package.json`, `vue3/vitest.config.ts`,
   `vue3/yarn.lock`, `vue3/src/utils/duration_utils.spec.ts` — as the branch tip, so it
   drops with a single reset.

The migration is renumbered if `0243` is taken on upstream's tip at the time the branch is
cut. No file under `requirements/`, `.devsteward/`, `.claude/`, `deploy/`, no `STEWARD.md`,
no `CLAUDE.md` change and no DevSteward evidence grader appears anywhere in the branch's
diff against `upstream/develop`.

### The proof before publishing

On the branch, before anything is pushed: the full Python suite passes, `yarn --cwd vue3
test` passes, `makemigrations --check` is clean, and the flake8 / isort / yapf / prettier
gate `guidelines.md` requires passes on every changed file. Pushing the branch to `origin`
runs the fork's GitHub workflows, giving a CI result before the PR is opened.

### The publication

Three outward-facing acts, all after the attended review:

- the **CLA** is signed by the owner at cla-assistant.io/TandoorRecipes/recipes;
- the **PR** is opened from `dr-froehlich/recipes:<branch>` to
  `TandoorRecipes/recipes:develop`, its description carrying the sanitized technical
  description, a `Closes #382` reference, and explicit offers to reshape — naming the
  vitest commit and the default-value commit as the seams;
- a short **comment on #382** links the PR.

### What the owner gets

The session that publishes leaves behind an account of what a pull request is in this

so the second contribution does not need this REQ again.

## Notes

**Required environment.** AC1–AC3 read git state: they need the `upstream` remote present
and fetched, and the PR branch existing locally. That is environment-bound in the sense
REQ-064 describes — recorded here deliberately rather than left to surface as a silent skip.
The oracle is coupled (this repository's own git history), so the criteria stay
`regression`; the develop session's first act is `git fetch upstream`. Publication
additionally needs `gh` authenticated — confirmed present at intake as `dr-froehlich` with
`repo` scope.

**Why the live proof sits in develop, not in validation.** The branch only exists somewhere
runnable after it is pushed, and a red CI run needs a repair loop. The System Tester runs in
a fresh session that never sees the diff and cannot fix anything, so routing "CI is green"
there would turn every red into a lost session. The push-and-iterate cycle is therefore a
develop-session obligation under the attended grant. AC4 keeps only what genuinely needs a
human oracle and no fixing loop: reading a published page against a checklist.

**Known gap, homed not deferred — the `h` key.** The hour unit is translated in one locale
of 36 and falls back to English in the rest. This REQ does **not** fix that, and the
omission is deliberate rather than silent: upstream's `translations.md` asks that
translations come through Weblate, so shipping hand-written catalogs would work against the
maintainer's stated process. The home is Weblate's normal cadence once the key is merged and
exposed to translators. Nothing is required in this fork either — the English fallback `h`
is correct German, which is what this household reads. If a household member ever reads
Tandoor in a CJK or Cyrillic locale, that is a fork-local REQ to intake then.

**Judgement calls settled at the attended review** (plan 0005 records all three in full).
`cookbook/tests/other/test_openapi_client_fresh.py` **does not ship** — the hole it closes is
this fork's client-regeneration trap (CLAUDE.md § Regenerating the API client), which upstream
does not have, and a bespoke freshness test for one field of one serializer would invite a
review question unrelated to duration formatting. The PR ships the plain `vitest run` test
script rather than REQ-003's `yarn install --frozen-lockfile --silent && vitest run`, whose
install prefix exists only to make this fork's acceptance gate hard-fail instead of skipping.
And the default-value flip is an offer in the PR description rather than a droppable commit,
per the amendment to Decision 2.

**AC4 was amended during develop, and why.** As intaken it required green checks and a
signed CLA outright. Opening the pull request proved both are gated on the maintainer:
upstream's CI is guarded by `if: github.repository_owner == 'TandoorRecipes'` so the fork
never runs it, and on the PR itself both check suites returned `conclusion: action_required`
with zero check runs — GitHub's first-time-contributor gate, which only a maintainer can
release. The CLA bot is installed (it commented on upstream PRs #4779 and #4781) but had not
raised its request, so there was nothing for the owner to sign either. Leaving the criterion
as written would have parked REQ-005 indefinitely on someone else's queue, which is exactly
what REQ-001 Decision 3 forbids. The criterion now accepts the approval-gated state provided
the equivalent verification is recorded: the develop session ran the full Python suite (1261
passed, 18 skipped), the vitest suite (20 passed), `yarn build` and `makemigrations --check`
on the branch, which is the same work upstream's CI performs. A check that actually runs and
goes red still fails.

**Out of scope.** Responding to review feedback — a flip request, a rename, a rebase onto a
newer develop — is a named follow-on REQ, to be intaken if and when feedback arrives. So is
merge. REQ-004 is not offered upstream by this REQ; the intake decision recorded there is
that it follows separately, later, after it has run in the household's own kitchen. Adding
the owner to `CONTRIBUTERS.md`, which `docs/contribute/contribute.md` invites, is left to
the attended session's discretion and is not an acceptance criterion.

**REQ-001 correction.** REQ-001's Notes state that `origin` still points at
`TandoorRecipes/recipes` and that a personal fork "can be added later". That is no longer
true — the fork exists as `origin` and upstream is a separate fetch-only remote. REQ-001 is
frozen and is not edited for this; the correct record is here.
